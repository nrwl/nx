Tracing plugin file reads in Nx

Spike branch ccr-12d2e183-r6seho on nrwl/nx. Linear NXC-5204.

Problem

Nx can't tell which files a plugin's createNodes depends on. It reruns every plugin on every project graph rebuild, or trusts each plugin's own cache to notice changes. Task inputs have the same gap. A task that reads a file outside its declared inputs gets a stale cache hit (#29074).

The spike records every file an isolated plugin worker opens and every directory it lists, including those of the processes it starts. Nx then reuses the plugin's last createNodes results until one of those files changes or one of those directories gains or loses an entry.

Architecture

nx daemon
  └─ plugin worker (node)          tracer library loaded into this process
       ├─ child process            ...and into every process it starts
       │    └─ grandchild          ...and so on down the tree
       └─ each process appends the files it opens and the directories
          it lists to one log file

daemon, after each createNodes call:
  read the log between "!begin <id>" and "!end <id>"
  fingerprint each file (inode, size, mtime, ctime unless hardlinked)
  hash each listed directory's entry names
  store results + fingerprints in .nx/workspace-data/plugin-evaluations/

The tracer has five layers. Only the first three differ by platform.

Interception Shim wraps libc's open family, opendir and scandir. The filter catches opens that bypass libc, execs, and directory rewinds. open, openat, fopen, execve, posix_spawn, __getdirentries64, getattrlistbulk IAT patches for NtCreateFile, NtOpenFile, NtQueryDirectoryFile(Ex), LdrLoadDll, CreateProcessW, GetProcAddress
Propagation Env var and filter are inherited Env var is inherited, and binaries that strip it run as re-signed copies Each new process is injected before it runs. A helper of the matching arch handles x86, x64 and arm64 children.

Why it's built this way

A library in every process

Without admin rights, the only way to see a process's file opens is to load code into it. Every OS has a kernel-level alternative, but each one needs privileges we can't ask users for (see OS facilities). BuildXL, tup and fspy use library injection for the same reason.

A log with per-call markers

A plugin worker lives for the whole daemon session and serves many createNodes calls. Nx has to know which reads belong to which call. The worker writes !begin <id> and !end <id> into the log around each call. Reads before the first marker are the plugin loading, and they count toward every call. A tracer that reports reads only when the process exits can't support this.

Re-signed copies on macOS

dyld drops DYLD_INSERT_LIBRARIES for SIP-protected and hardened binaries. That covers /bin/sh, /usr/bin/git, xcrun and the system python3, so plugins hit it all the time. The tracer checks the code signature before each exec. If the target would strip the library, it runs an ad hoc re-signed copy instead, cached in an owner-only directory under the nx temp dir. Copies keep their original basename, because multi-call shims such as xcrun and mise dispatch on it.

Re-signed Apple binaries are arm64e, so the dylib needs an arm64e slice. That's why the macOS tracer is C. Rust supports arm64e only as a tier 3 nightly target with -Zbuild-std, and stable Rust can't define a C-variadic function such as open.

Rust on Linux

Linux has no arm64e. The one problem is open's variadic signature, and a fixed-signature definition is ABI-compatible on every Linux target we ship. So the Linux tracer is a crate in the root Cargo workspace.

Seccomp on Linux

LD_PRELOAD only sees calls that go through libc. Static binaries such as esbuild, Go programs (which make raw syscalls even when dynamically linked), Bun, and the dynamic loader all skip it. So the worker starts under fstrace-linux. The launcher forks, and the child sets no_new_privs, installs a seccomp user-notification filter, and execs the worker. The filter is inherited by every descendant.

The kernel parks each matching syscall until the launcher has read its path from the tracee's memory, logged it, and let it continue. The shim's own opens carry a marker argument that the filter lets through without a round trip, so dynamic binaries stay at shim speed. A notified syscall costs about 30 µs. Node startup went from 34 ms to 37 ms in an aarch64 VM.

The launcher also forwards signals and exits with the worker's status. Processes that outlive the worker, such as a build tool's daemon, keep the filter. While the worker runs, the launcher adopts them as a child subreaper, so they stay its descendants and it can still read their memory under Yama's default ptrace_scope of 1. After the worker exits, a detached process lets their syscalls through until the last one exits, because they would fail with ENOSYS once nobody holds the listener.

Directory listings

A listing records a directory's entry names, not the entries' contents. A file's contents count only if the file was also read. Each platform hooks the one call every directory API ends in, so readdir, scandir, fts, libuv, dir and PowerShell are all covered.

  • On Linux, opening a directory readably, in the shim or the filter, and rewinding it with lseek. Listing needs a readable fd, so each directory costs one log line and at most one launcher round trip, instead of a round trip on every getdents64 call.
  • On macOS, __getdirentries64. libsystem_c imports it from libsystem_kernel, so interposing reaches it. getattrlistbulk is hooked too.
  • On Windows, NtQueryDirectoryFile and NtQueryDirectoryFileEx. libuv finds those with GetProcAddress rather than importing them, so the DLL also hooks GetProcAddress to hand back the hooked versions.

Hand-rolled injection on Windows

The launcher creates the worker suspended inside a job object and queues LoadLibraryW as an APC, so the DLL loads before any of the worker's own code runs. The DLL patches the import tables that reach the four ntdll calls above, and injects each child the same way. A child of another architecture can't be injected from the parent's, so the parent asks a launcher of the child's architecture to do it. Microsoft Detours does the same job and supports arm64. We haven't compared the two, and Detours is worth trying if the hand-rolled patching causes trouble.

Keeping the cache correct with plugin caches on

Plugins such as @nx/js/typescript keep their own result caches. A cache hit means the plugin skips reading that project's files, so one call's trace doesn't cover every project. Nx handles this in three ways:

  • A new entry's inputs and listings are this call's plus the previous entry's.
  • A plugin's first traced call runs with NX_CACHE_PROJECT_GRAPH=false for that call only, so the starting entry is complete.
  • The plugin's own cache files under .nx/workspace-data aren't inputs, because plugins rewrite them every run.

On the nx repo, @nx/js/typescript matches 372 tsconfigs. Its entry holds 1,578 inputs and 365 listings. An unchanged run returns cached results in about 25 ms, and so does editing a file that was only listed. Adding a file to a listed directory reruns the plugin.

These crates cover injection at most. None of them follows a process tree or handles SIP, and those are where most of our code goes.

fspy

fspy is VoidZero's file access tracer for vite-task, the task runner behind vp run in Vite+. It's Rust, MIT licensed and actively maintained. It's the closest match to what we built, and it does some things better:

  • It uses seccomp user notification on Linux for static binaries, as our launcher now does.
  • It also hooks stat and access. Ours records opens and directory listings only.
  • It uses Microsoft Detours on Windows.

We can't adopt it as a dependency today:

Issue Detail
Not published Every fspy crate sets publish = false. We'd need a git dependency or a vendored copy.
Nightly Rust It embeds its preload library with cargo's -Zbindeps, and the repo pins a nightly toolchain. Nx builds on stable. Whether the preload crate builds on stable outside their workspace is untested.
Results arrive at exit TrackedChild returns path accesses when the root process exits. A plugin worker never exits between calls, so we can't attribute reads to one call.
It owns the spawn fspy spawns the process from Rust with tokio. Nx starts plugin workers with Node's child_process.
Narrower macOS coverage It swaps /bin/sh and /bin/bash for a bundled oils shell and coreutils for uutils, which build.rs downloads from GitHub. Other binaries in /bin and /usr/bin, such as git and python3, run without tracing. Running oils as the system shell also changes how user scripts behave.

Where fspy could still fit

  • Task inputs (#29074). A task is one process that exits, which is exactly fspy's model. Its exit-time results are fine there, and the nightly and spawn problems are smaller because the task runner already spawns from Rust.

That depends on building fspy's crates on stable outside the vite-task workspace.

Known gaps in the current design

  • Failed opens, stat and access aren't recorded. The names under config directories and project roots are hashed whether or not the plugin listed them, which covers most existence checks, but not checks elsewhere.
  • Linux needs kernel 5.8 or later. On older kernels, such as RHEL 8's 4.18, the launcher logs !untraced and results are never reused. The same happens on 32-bit Arm, and whenever a process in the tree makes 32-bit or x32 syscalls on a 64-bit kernel.
  • Under the launcher, setuid binaries such as sudo don't gain privileges, because of no_new_privs.
  • On Linux, opens through io_uring aren't seen. The filter makes io_uring_setup fail, so callers fall back to plain syscalls.
  • Carried-forward inputs only grow until nx reset. That costs extra plugin runs, never stale results.
  • Any change to an NX_* env var invalidates every entry.
  • Nx has run end to end with tracing only on macOS. The Linux launcher was tested with Node, static and raw-syscall binaries in an aarch64 container. Windows was tested only on arm64.
  • createDependencies isn't cached, so plugins with it still start a worker on every daemon start.
  • Windows doesn't log writes, so a plugin whose config loader writes and removes a temporary file, as vite does, is never cached there.
  • A plugin that lists a directory in which its own subprocess creates and removes a temporary file, as pnpm's CLI does in the workspace root, sees that directory change during the call and is never stored.
